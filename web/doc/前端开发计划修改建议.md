# 前端开发计划修改建议

可以，但我建议**不要直接按现在这份前端开发计划开工**。我把 `frontend.md` 和 `frontend-project-dev-doc-plan.md`，结合你前面
Phase 1～12 的后端设计一起对了一遍，结论是：

**整体方向正确，可以执行；但前端开发文档在正式落地前需要补 6 个关键修改，其中 2 个属于后端接口契约问题，最好现在就修。**

前端现状目前只有“表单、文件、AI 填报”三大能力，没有 Project 页面和 Assistant 页面，因此新增 Project + Assistant 的前端分层方案是合理的。

## 一、最重要的问题：`POST /project` 和绑定表单返回裸 Long

你的前端开发计划已经发现这个问题：

```text
POST /project
→ Result<Long>

POST /project/{id}/form
→ Result<Long>
```

而前端现有约定又明确要求雪花 ID 一律字符串化，因为 JS `Number` 存在精度风险。

目前前端计划写的是：

> “建议以 projectNo/detail 接口回查定位；推动后端补 ToStringSerializer 为首选”

这里我建议**不要让前端自己兜底**。

### 应该直接修改后端

把：

```java
Result<Long>
```

改成一个 ID VO，或者至少返回字符串。

例如：

```java
public class IdVO {

    @JsonSerialize(using = ToStringSerializer.class)
    private Long id;
}
```

然后：

```java
Result<IdVO>
```

或者如果项目当前习惯允许：

```java
Result<String>
```

这样前后端契约从源头一致。

这是我认为目前**最应该修改的地方**。

因为前端文档自己已经明确规定：

> “ID 一律字符串化”

而当前后端又有裸 Long，这是契约不一致。

# 二、`POST /task` 的 ProjectId 前端改造是必须的

这个地方你的计划是对的。

现有前端：

```ts
startTask({
    formId,
    fileId
})
```

而后端已经增加：

```text
projectId?
formId
fileId
```

前端必须变成：

```ts
startTask({
    projectId,
    formId,
    fileId
})
```

并且必须兼容：

```text
projectId = undefined
```

因为后端明确保留历史 API。你的前端文档也已经识别到了这个改动。

同时，`AiFill.vue` 不能只从“全部文件”选择。

项目详情页进入 AI 填报时应该：

```text
Project
  ↓
projectId
  ↓
AiFill
  ↓
只能选择当前项目文件
```

否则用户在项目 A 中可能选择了项目 B 的文件。

------

# 三、文件上传必须真正建立 Project Context

现在前端文件上传：

```text
POST /file/upload
```

而后端已经支持：

```text
POST /file/upload?projectId=1001
```

你的前端计划：

> `FileUpload` 支持 `route query.projectId` 预选

这个方向正确，但还应该补一条：

**上传页面必须明确展示当前项目名称，并禁止用户误以为文件已经关联项目。**

建议：

```text
项目：职教园一期

[拖拽上传]

归属项目：
职教园一期

上传后：
file.projectId = 当前 projectId
```

同时上传成功后的 `lastUpload` 现在只有：

```text
fileId
fileName
fileType
createTime
```

建议增加：

```text
projectId
projectName
```

因为你的 `lastUpload.ts` 现在负责跨页面把最近文件带到 AI 填报页。

否则可能出现：

```text
项目 A 上传文件
↓
跳到 AiFill
↓
localStorage 只知道 fileId
↓
项目上下文丢失
```

### 建议修改

```ts
interface LastUpload {
  fileId: string
  fileName: string
  fileType: FileType
  projectId?: string
  projectName?: string
  createTime: string
}
```

------

# 四、项目详情页的结构设计是合理的，但建议调整 Assistant 入口

现在计划：

```text
/project/:id
 ├─ 基础信息
 ├─ 文件
 ├─ 表单
 └─ 助手入口
```

这个没问题。

但我建议不要把 Assistant 做成完全独立：

```text
/project-assistant
```

而是：

```text
/project/:id
```

里面：

```text
Tab：
概览
文件
表单
智能助手
```

或者右侧固定：

```text
┌─────────────────────────────┐
│ 项目详情                     │
│                             │
│ 概览 | 文件 | 表单 | 智能助手 │
└─────────────────────────────┘
```

原因很简单：

后端 Assistant API 已经是：

```text
/project/{projectId}/assistant/chat
```

它本身就是项目作用域。

前端 UI 也应该让：

> **Project 是上下文，Assistant 是 Project 的一个能力。**

而不是独立聊天应用。

------

# 五、Assistant 的前端数据模型还需要补“对话消息类型”

你现在计划已经覆盖：

```text
AssistantChatRequest
AssistantChatResponse
AssistantReferenceVO
ProjectStructuredFactsVO
CrossProjectComparisonVO
```

但实际上还缺一个很关键的前端 UI Model：

```ts
interface ChatMessage {
  role: 'user' | 'assistant'
  content: string
  timestamp: string
  response?: AssistantChatResponse
  loading?: boolean
}
```

因为后端返回的是一轮：

```text
AssistantChatResponse
```

但前端需要维护：

```text
消息列表
  ↓
用户消息
助手消息
用户消息
助手消息
...
```

所以建议：

```text
types/assistant.ts
```

里面区分：

```text
API DTO/VO
+
UI ChatMessage
```

不要直接把 `AssistantChatResponse[]` 当聊天记录。

# 六、`conversationId` 前端存储策略需要明确

你们 Phase 9 已经确定：

```text
Redis key =
assistant:{projectId}:{conversationId}
```

所以前端必须保证：

```text
/project/1001
conversationId = abc

/project/1002
conversationId = def
```

不能全局：

```text
conversationId = abc
```

你的计划已经写了：

> ChatPanel：conversationId 生成与存储（按 projectId 隔离）

这个必须明确成代码规则：

```ts
localStorage key：

aifp_assistant_conversation_${projectId}
```

而不是：

```ts
aifp_conversation
```

否则前端虽然传了不同 projectId，用户体验层面仍可能发生会话串线。

------

# 七、Citation 的设计前端方向正确，但建议不要直接正则解析 answer

Phase 11 已经规定：

```text
answer：
项目总投资为 12.5 亿元。[S1]

citations：
[
  {
    citationId: "S1",
    ...
  }
]
```

前端文档计划：

> `[S{n}]/[D{n}]` → citations 渲染上标/来源卡片

这是对的。

但建议前端：

**不要把 `answer` 字符串解析成 citation 数据作为唯一依据。**

后端已经提供：

```text
citations[]
```

前端应该：

```text
answer
+
citations
```

共同渲染。

也就是说：

```text
answer = 原始答案
citations = 结构化证据
```

前端最多扫描 `[S1]` 作为显示锚点。

不要重新根据 `S1` 自己构建来源对象。

否则会出现：

```text
后端 citationId
≠
前端解析规则
```

造成第二套 citation 逻辑。

------

# 八、`structuredData` 建议不要只做一个普通表格

你现在计划已经考虑 conflict 卡片，这个非常好。

例如：

```text
项目总投资

⚠ 存在多个来源

12.5亿元
来源：施工许可证.pdf 第3页

13亿元
来源：立项批复.pdf 第5页
```

不要直接：

```text
项目总投资 | 12.5亿
```

否则完全体现不出 Phase 7 的核心设计：

> 冲突不裁决，全部值返回。

因此前端要把：

```text
conflict = false
```

和：

```text
conflict = true
```

设计成两种视觉状态。

------

# 九、`comparisonData` 应该独立组件

Phase 10 已经后端确定性计算：

```text
rank
aggregate
diffFromCurrent
excluded
```

前端不应该自己计算。

所以建议：

```text
ComparisonResult.vue
```

专门渲染：

```text
比较字段：项目总投资

排名：

1. 项目A   15亿元
2. 当前项目 12.5亿元
3. 项目B   8亿元

当前项目差值：

项目A：+2.5亿元
项目B：-4.5亿元

聚合：
最大：15亿
最小：8亿
平均：11.8亿
```

前端**只展示后端计算结果**。

这一点必须写死，否则后续前端开发者很容易看到：

```ts
normalizedValue
```

之后自己计算一遍。

# 十、文件列表 100 条这个限制，前端文档要加警告

你的后端 Phase 8 当前 Assistant 文件清单使用：

```text
PageQuery(1,100)
```

前端计划也接受了这个设计。

可以第一版这样做。

但“项目文件 Tab”不能依赖这个 100 条限制。

应该：

```text
项目文件 Tab
→ GET /project/{id}/files
→ 正常分页
```

而：

```text
Assistant “有哪些文件”
→ AssistantResponse.usedFiles / 当前 Assistant file list
```

是两个不同场景。

这个需要写清楚。

# 十一、前端项目开发计划建议增加一个后端契约修复 Phase 0

你现在的前端计划直接从：

```text
A 项目 CRUD
```

开始。

我建议改成：

```text
Phase 0：前后端契约修复
    ↓
Phase A：Project CRUD
    ↓
Phase B：File / Form 关联
    ↓
Phase C：Upload / Task
    ↓
Phase D：Assistant 基础聊天
    ↓
Phase E：Citation / Conflict / Comparison
    ↓
Phase F：Regression
```

### Phase 0 必须包含

第一优先：

```text
POST /project
POST /project/{id}/form
```

解决裸 `Long` ID。

第二：

统一所有项目相关 ID 的 TS 类型：

```ts
type SnowflakeId = string
```

不要到处写：

```ts
number | string
```

前端现在已经明确要求所有雪花 ID 字符串化。

这样：

```ts
projectId: SnowflakeId
fileId: SnowflakeId
formId: SnowflakeId
projectFormId: SnowflakeId
conversationId: string
```

整个项目会干净很多。

# 十二、前端文档本身需要补一个“后端契约差异说明”

你的 `frontend-project-dev-doc-plan.md` 里目前已经意识到：

> API 以实际后端代码为准，而不是需求稿。

这个原则非常正确。

但建议正式文档增加一个专门章节：

### “前后端契约注意事项”

至少列：

| 问题                       | 当前状态   | 前端处理          |
|--------------------------|--------|---------------|
| Project 创建 ID            | 裸 Long | **建议后端改字符串**  |
| ProjectForm 创建 ID        | 裸 Long | **建议后端改字符串**  |
| Task projectId           | 可选     | Project 页面必须传 |
| File upload projectId    | 可选     | Project 页面传   |
| Assistant conversationId | 可选     | 前端生成/缓存       |
| references               | 全量证据   | 来源集合          |
| citations                | 实际引用   | 上标/来源卡        |
| structuredData           | 项目事实   | 冲突展示          |
| comparisonData           | 后端计算   | 排名/聚合展示       |

这样未来前后端联调时会很清楚。

------

# 最终结论

**可以执行，但不要原样直接开发。**

我建议先做这几个修改：

**必须修改：**

1. 后端 `POST /project` 的裸 Long ID
2. 后端 `POST /project/{id}/form` 的裸 Long ID
3. 前端统一 `SnowflakeId = string`
4. `lastUpload` 增加 `projectId`
5. Assistant 增加 UI 层 `ChatMessage`
6. 明确 `conversationId` 按 `projectId` 持久化
7. `structuredData / comparisonData / citations` 分组件渲染
8. 项目文件列表与 Assistant 文件清单分开处理

**然后再执行前端阶段：**

```text
Phase 0  前后端契约修正
   ↓
Phase A  Project CRUD
   ↓
Phase B  Project File/Form
   ↓
Phase C  Upload + Task
   ↓
Phase D  Project Assistant
   ↓
Phase E  Citation + Conflict + Comparison
   ↓
Phase F  全量回归
```

你的现有前端架构本身不需要推翻，继续使用：

```text
types
  ↓
api
  ↓
stores
  ↓
views/components
  ↓
router/MainLayout
```

即可。现有前端文档已经把这套分层和 ID 字符串化、Axios Result 拆包、SSE 生命周期等约定定义得比较完整。

**尤其是后端裸 Long 这一点，我建议先改后端再开始前端开发，不建议让前端用“回查详情”去规避。** 这属于 API 契约层的问题，越早修成本越低。
