# 项目需求新增

从现有代码设计看，当前系统已经形成了比较清晰的三层基础：PDF 先形成清洗后的 DocumentAst，再通过 HybridSemanticChunker 入
Milvus；字段抽取阶段按 fileId 做检索隔离并通过 Schema 校验得到结构化字段；Web 层则由 File / Form / Task / Fill 四类能力组成。

因此，这次新增功能不建议把“项目”简单当成一个 fileId 的集合，也不建议只靠 Milvus 做“项目金额是多少”“两个项目哪个更大”这类问题。更合适的设计是：

**Project 作为业务聚合根 → Project/Form/File 建立关系 → 表单抽取结果形成项目结构化数据 → 文档 Chunk 继续进入 Milvus →
项目助手同时使用结构化查询 + 项目范围 RAG → 跨项目比较优先走结构化数据。**

下面这个 Prompt 可以直接给你的代码智能体使用。

你现在需要在现有 AI 文件解析 / RAG / 表单抽取系统基础上，新增“项目（Project）”一级业务概念，并增加“项目对话助手（Project
Assistant）”。

本次改造必须基于现有代码和当前架构进行增量修改，禁止推翻现有 PDF
解析、DocumentAst、HybridSemanticChunker、Milvus、FieldExtractorService、Form、File、异步任务和 SSE 进度体系。

一、现有系统必须保留的核心架构

当前系统已经具备：

​ \1. 文件上传

​ ○ FileController

​ ○ FileService

​ ○ FileRecord

​ ○ FileStatus 状态机

​ \2. 表单定义

​ ○ FormController

​ ○ FormService

​ ○ FormDefinition

​ ○ FormFieldDefinition

​ \3. 文件解析

​ ○ PDF / Excel / Word

​ ○ PDF 结构化解析最终统一形成 DocumentAst

​ ○ DocumentAst 是 Markdown 和语义切块的标准来源

​ ○ PDF 页面支持 TEXT_ONLY / IMAGE_ONLY / MIXED / EMPTY

​ ○ MIXED 页面支持 PDF 原生文字 + OCR + 表格结构融合

​ ○ DocumentCleaner 完成字符、换行、表格、OCR、页眉页脚、重复内容清洗

​ \4. RAG

​ ○ DocumentIngestionService

​ ○ HybridSemanticChunker

​ ○ ChunkVectorConverter

​ ○ Milvus

​ ○ metadata 包含 fileId、fileName、pageStart、pageEnd、titlePath、chunkType、chunkIndex、totalChunks、sourceType 等

​ \5. AI 字段抽取

​ ○ FieldExtractorService

​ ○ FieldQueryGenerator

​ ○ ExtractionPromptBuilder

​ ○ FieldSchemaValidator

​ ○ 目前通过 fileId 过滤向量检索

​ ○ LLM 抽取后进行字段类型校验和失败重试

​ \6. 异步解析任务

​ ○ ParseTaskService

​ ○ AsyncParseExecutor

​ ○ Redis

​ ○ SSE

​ ○ ProgressPublisher

​ \7. Web API 当前已有：

​ ○ /file

​ ○ /form

​ ○ /task

​ ○ /fill

上述能力必须继续兼容。

现有文档中已经明确：PDF 的 parseStructured 最终产物是清洗后的 DocumentAst，并由 HybridSemanticChunker 消费；这条链路是当前主结构化
RAG 链路，不能在本次改造中绕开。

同时，当前向量检索已经使用 fileId 过滤防止跨文件污染，新的项目助手必须在此基础上增加“项目级作用域”，不能取消原有 fileId 隔离。

二、本次新增业务目标

新增“项目”概念。

一个项目可以关联：

Project

├── 多个 Form

│ ├── 多个 FormField

│ └── 多次文件解析 / 表单填报

│

├── 多个 File

│ └── 每个 File 对应解析后的 Chunk

│

└── 项目结构化字段数据

用户可以在项目下：

​ \1. 上传多个项目相关文件

​ \2. 使用不同 Form 对这些文件进行 AI 自动填报

​ \3. 将解析得到的表单结果保存到同一个 Project

​ \4. 修改 / 补充项目表单数据

​ \5. 查看项目全部资料

​ \6. 打开项目助手

​ \7. 针对当前项目进行自然语言提问，例如：

“这个项目的项目金额是多少？”

“项目总建筑面积是多少？”

“这个项目什么时候开工？”

“这个项目有哪些施工单位？”

“这个项目有哪些文档？”

“根据已经上传的材料，这个项目的总投资是多少？”

“为什么这个项目的投资金额有两个值？”

“哪个文档提到了项目面积？”

“这个项目的计划投资和实际投资分别是多少？”

还需要支持跨项目分析，例如：

“当前项目和项目A的投资金额有什么差异？”

“当前项目和其他项目相比，哪个面积最大？”

“比较项目A、项目B、项目C的总投资和建筑面积。”

“当前项目的投资额在所有项目中排名第几？”

“哪些项目的总建筑面积超过当前项目？”

“帮我分析当前项目为什么比其他项目投资高。”

所以本次设计不是简单增加一个 ChatController，而是建立：

Project Domain + Project Data Model + Project Scoped RAG + Structured Query + Project Assistant。

三、核心设计原则

​ \1. Project 是业务聚合根

Project 是项目级数据的归属对象。

Project

​ ● createdTime

四、为什么必须增加结构化项目数据层

项目助手不能只使用 Milvus。

例如：

用户：

“项目金额是多少？”

“当前项目和项目A相比谁更大？”

“所有项目中哪个项目投资金额最大？”

这类问题，本质属于结构化数据查询。

如果只通过向量检索：

“项目金额”

然后召回文本 chunk，再让 LLM 推断：

会存在：

​ \1. 数值不准确

​ \2. 同一个项目多个文档金额冲突

​ \3. 单位换算错误

​ \4. 无法排序

​ \5. 无法进行所有项目统计

​ \6. 无法计算差值 / 百分比

​ \7. 无法稳定进行跨项目比较

因此必须采用“双通道架构”。

Project Assistant

|

+---- Structured Query

| |

| +-- Project

| +-- ProjectForm

| +-- ProjectFormFieldValue

|

+---- Vector RAG

|

+-- Project Files

+-- Milvus Chunks

最后由 LLM 综合回答。

五、项目级 RAG 设计

当前：

fileId -> Milvus Chunk

新增：

projectId -> fileId -> Milvus Chunk

不要删除 fileId。

新的 chunk metadata 至少增加：

projectId

即：

fileId

projectId

fileName

pageStart

pageEnd

titlePath

chunkType

chunkIndex

totalChunks

sourceType

检索范围设计：

​ \1. 当前文件：

fileId

​ \2. 当前项目：

projectId

​ \3. 跨项目：

projectId IN (...)

原有 FileId Filter 必须继续存在。

例如：

fileId == '1001'

仍然有效。

项目助手查询当前项目时：

projectId == '2001'

项目助手查询指定多个项目时：

projectId in (...)

但是具体过滤表达式必须根据现有 VectorStore / Milvus 实现调整，不要假设 Milvus 当前驱动一定支持某种 SQL 写法。

六、项目和文件的关系

一个文件可以属于一个 Project。

新增：

FileRecord.projectId

或者如果现有 FileRecord 不适合直接增加 projectId，则创建：

ProjectFile

​ ● id

​ ● projectId

​ ● fileId

​ ● relationType

​ ● createTime

优先根据现有代码风格选择。

如果一个 File 永远只能归属一个 Project，则优先直接增加：

file.project_id

这样结构简单。

如果未来明确需要同一个文件被多个项目复用，才使用 ProjectFile 中间表。

不要为了“可能以后需要”而过度设计。

十一、字段值必须保存原始值和标准值

例如：

文档：

“项目总投资：12.5亿元”

建议保存：

fieldValue = "12.5亿元"

normalizedValue = 1250000000

unit = "元"

这样：

LLM 回答用户时可以展示：

12.5 亿元

而进行比较时：

1250000000

用于排序和计算。

FieldSchemaValidator 当前已经支持 INTEGER / DECIMAL 的“万 / 亿”转换，因此项目结构化数据可以复用这套转换逻辑，不要重新实现一套金额解析。

十二、必须保存数据来源

项目助手回答“项目金额是多少”时，不能只给一个数字。

应该能够追溯：

项目：

职业教育园一期

字段：

项目总投资

值：

12.5亿元

来源：

职教园一期施工许可证.pdf

页码：

第3页

必要时还要能够关联：

sourceChunkId

因此 ProjectFormFieldValue 至少建议支持：

sourceFileId

sourcePage

sourceChunkId

这样可以实现“回答 + 证据”。

十五、不要让 LLM 直接访问数据库

非常重要。

LLM 不应该直接拼 SQL。

应该：

用户问题

↓

Intent / Query Plan

↓

后端构造 Query

↓

Service / Repository 查询

↓

返回结构化结果

↓

LLM 解释

例如：

用户：

“当前项目和项目A哪个投资额更大？”

LLM 不应该输出：

SELECT * FROM project...

而应该先解析为：

{

"intent": "PROJECT_COMPARISON",

"metric": "TOTAL_INVESTMENT",

"projectIds": ["CURRENT", "PROJECT_A"]

}

后端：

ProjectDataQueryService.queryMetric(...)

最终得到：

项目A = 10亿元

当前项目 = 12.5亿元

再交给 LLM：

“当前项目 12.5 亿元，项目A 10亿元，当前项目高 2.5亿元，高 25%。”

十六、建议的 Query Intent

第一版至少支持：

PROJECT_FIELD_QUERY

例如：

“项目金额是多少？”

“项目面积多少？”

“建筑面积是多少？”

PROJECT_DOCUMENT_QUERY

例如：

“有哪些文件？”

“哪个文件提到了项目金额？”

“合同中怎么描述项目工期？”

PROJECT_COMPARISON

例如：

“当前项目和项目A投资额比较。”

PROJECT_RANKING

例如：

“投资金额最大的项目是哪一个？”

PROJECT_AGGREGATION

例如：

“所有项目总投资是多少？”

PROJECT_FILTER

例如：

“哪些项目建筑面积超过10万平方米？”

PROJECT_ANALYSIS

例如：

“这个项目为什么投资比较高？”

UNKNOWN

无法识别时转普通 RAG 或要求用户明确范围。

十七、项目助手的关键策略

对于不同问题必须选择正确数据源。

​ \1. 单字段事实问题：

“项目金额是多少？”

优先：

ProjectFormFieldValue

如果没有可靠结构化值：

Project Scoped RAG

​ \2. 文档内容问题：

“施工许可证里怎么写的？”

直接：

Project Scoped RAG

​ \3. 统计问题：

“所有项目平均投资多少？”

必须：

Structured Query

​ \4. 排序问题：

“哪个项目面积最大？”

必须：

Structured Query

​ \5. 比较问题：

“项目A和项目B哪个更大？”

必须：

Structured Query

​ \6. 原因分析：

“为什么项目A投资比项目B高？”

Structured Query

+

RAG

+

LLM

也就是：

结构化数据负责事实

RAG 负责文档证据

LLM 负责解释和归纳

十八、项目助手不能只按向量相似度回答数字问题

必须避免：

用户：

“项目金额是多少？”

系统：

直接召回几个 chunk

然后 LLM 自己猜。

正确：

​ \1. 先查询 ProjectFormFieldValue

​ \2. 找到项目金额

​ \3. 检查是否有多个版本 / 多来源

​ \4. 如果有冲突：

​ ○ 返回多个值

​ ○ 说明来源

​ ○ 不得擅自选择一个作为绝对事实

​ \5. 必要时再 RAG 查询原文

十九、多个文档存在冲突时的处理策略

例如：

文件A：

项目总投资 = 10亿元

文件B：

项目总投资 = 12亿元

不能直接认为 12 亿一定正确。

需要设计：

FieldValueConflictResolver

负责：

​ \1. 同字段多值检测

​ \2. 来源统计

​ \3. 时间 / 版本判断

​ \4. 优先级策略

​ \5. 输出冲突信息

初版可以：

如果同一项目同一字段存在多个不同值：

返回：

“当前项目存在两个项目总投资值：

A文档：10亿元

B文档：12亿元。

目前无法仅根据现有资料确认最终口径。”

如果字段具有明确更新时间 / 版本，则后续再扩展优先级策略。

禁止 LLM 凭感觉选择。

二十二、Prompt 不允许伪造事实

项目助手系统 Prompt 必须明确：

​ \1. 只能依据提供的项目结构化数据和检索文档回答

​ \2. 不得自行编造项目数据

​ \3. 不确定时必须明确说明

​ \4. 数据冲突时必须指出冲突

​ \5. 数字比较必须使用后端提供的标准化数值

​ \6. 不得自行进行未经确认的单位推断

​ \7. 涉及项目比较时必须明确比较对象

​ \8. 引用文件时必须给出文件名，能拿到页码时必须给页码

​ \9. 如果结构化数据为空，再使用 RAG 补充

​ \10. RAG 没有可靠依据时，不得编造答案

二十三、项目助手 Prompt 建议

System Prompt 结构建议：

你是“项目智能助手”。

你的任务是回答项目相关问题。

你只能依据系统提供的以下信息：

​ \1. 项目基础信息

​ \2. 项目结构化字段

​ \3. 项目文档检索结果

​ \4. 跨项目结构化查询结果

​ \5. 文档来源信息

​ \6. 对话历史

禁止根据常识猜测项目数据。

对于数字类问题：

​ ● 优先使用结构化字段

​ ● 使用 normalizedValue 做计算

​ ● 使用 fieldValue 做展示

​ ● 明确单位

​ ● 明确数据来源

对于比较问题：

​ ● 必须使用后端提供的结构化比较数据

​ ● 不允许直接从自然语言中自行比较未经标准化的数据

对于文档问题：

四十六、最重要的一条

不要把“项目助手”实现成一个简单的：

Project Assistant”**。其中项目字段值单独持久化非常关键，否则“项目比较、排序、统计”最后都会退化成让大模型从文本里猜数字。
